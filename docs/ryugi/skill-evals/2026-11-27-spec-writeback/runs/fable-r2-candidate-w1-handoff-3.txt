## 4. 在运行中的应用里抓证据(整条链路和相邻流程)

浏览器检查是项目验证阶段做的。报告需要可读的原始输出,所以在同一个 dev server、同一个提交上重新抓一次。

```bash
cd /Users/p/git/notes-app && OUT=.artideck/artifacts/verify/export/streamed-download.txt && TMP=$(mktemp -d) && COUNT='
const fs=require("fs");const s=fs.readFileSync(process.argv[1],"utf8");
let q=false,rows=0,cur=false;
for(let i=0;i<s.length;i++){const c=s[i];
  if(c==="\""){ if(q&&s[i+1]==="\""){i++;} else q=!q; cur=true; }
  else if(c==="\n"&&!q){ if(cur) rows++; cur=false; }
  else if(c!=="\r") cur=true; }
if(cur) rows++;
console.log("header="+s.slice(0,s.indexOf("\n")).trim()+" records="+(rows-1)+" unterminated_quote="+q);' && {
  echo "## env"; date -u +%Y-%m-%dT%H:%M:%SZ; git rev-parse --short HEAD; echo "pnpm dev @ http://localhost:8787";
  echo "## 1. demo (20000 notes)";
  curl -sS -N -b .dev/demo.cookie -D - -o "$TMP/big.csv" \
    -w 'http=%{http_code} bytes=%{size_download} ttfb=%{time_starttransfer}s total=%{time_total}s\n' \
    http://localhost:8787/api/notes/export.csv;
  node -e "$COUNT" "$TMP/big.csv";
  echo "## 2. neighbour: demo2 (3 notes, below the 10000 threshold)";
  curl -sS -b .dev/demo2.cookie -o "$TMP/small.csv" -w 'http=%{http_code} bytes=%{size_download}\n' http://localhost:8787/api/notes/export.csv;
  node -e "$COUNT" "$TMP/small.csv";
  echo "## 3. neighbour: permissions — demo2's export vs demo's ids";
  cut -d, -f1 "$TMP/small.csv" | tail -n +2 | sort > "$TMP/small.ids"; cut -d, -f1 "$TMP/big.csv" | tail -n +2 | sort > "$TMP/big.ids";
  echo "ids_shared=$(comm -12 "$TMP/small.ids" "$TMP/big.ids" | wc -l | tr -d ' ')";
  echo "## 4. neighbour: no session";
  curl -sS -o /dev/null -w 'http=%{http_code}\n' http://localhost:8787/api/notes/export.csv;
} > "$OUT" 2>&1; rm -rf "$TMP"; cat "$OUT"
```

```xml
  <claim id="streamed-20000" judge="agent" from="本地 pnpm dev(localhost:8787),feat/export @ a41c9e7" capturedAt="2026-11-28T15:42:10+08:00">
    <title>20000 条笔记可以流式下载,文件完整</title>
    <result>HTTP 200,chunked 无 Content-Length,首字节 0.041s、全程 3.87s;按 RFC 4180 解析得到表头加 20000 条记录,没有未闭合的引号。</result>
    <output file="streamed-download.txt"/>
  </claim>

  <claim id="ruling-streaming" judge="human" from="feat/export @ a41c9e7,Task 2 的决定" capturedAt="2026-11-28T15:42:10+08:00">
    <title>大批量导出改成了流式:每 500 条写一次,不在服务端生成完整文件</title>
    <ask>设计文档写的是"先在服务端生成完整文件,再一次性下载",这里没有照做。如果用户需要断点续传(下载中断后从断点继续),这个决定就是错的:流式响应没有 Content-Length,也不支持 Range,中断后只能重新下载。</ask>
    <p>原因:一万条以上的完整文件在 Worker 上超出内存,按设计文档的做法无法生成。改成流式后内存占用只和一批(500 条)有关。代价是浏览器下载时显示不了总大小和剩余时间,中途出错时用户拿到的是一个不完整的文件。</p>
  </claim>

  <claim id="ruling-quoting" judge="human" from="feat/export @ a41c9e7,Task 1 的决定" capturedAt="2026-11-28T15:42:10+08:00">
    <title>字段按 RFC 4180 加引号</title>
    <ask>设计文档只写了"逗号分隔",没说标题或正文里有逗号、引号、换行时怎么办,这一点是我定的。如果导出的文件主要是给人直接看原始文本,或交给不认 RFC 4180 引号的工具处理,这个决定就是错的:他们会看到多出来的引号。</ask>
    <p>原因:不加引号的话,正文里的一个逗号或换行就会让这一行错列,文件无法被可靠地读回。RFC 4180 是 Excel、Numbers 和各语言 CSV 库都认的写法。</p>
  </claim>

  <gap id="worker-memory">未在真实的 Worker 运行环境上验证 20000 条导出的内存占用。以上证据来自本地 pnpm dev,本地运行时不执行线上的内存上限,而"超出内存"正是改成流式的理由。我没有做是因为部署到预览环境是工作区之外的动作,需要你先同意。需要你做的一件事:允许我部署到预览环境后再测,或者豁免这一项。</gap>
</verify>
```
