  <h1>CSV 导出：验证</h1>
  <p>1 条由我验证，2 条等你判断，1 个缺口。例行检查：pnpm test 32/32 通过（a41c9e2）。同一接口的相邻流程也走过：3 条笔记的小导出只返回本人的 3 行，未登录返回 401。项目自带的浏览器检查已下载成功，作为辅助证据。</p>

    <title>20000 条笔记以流式方式完整下载</title>
    <result>分块传输，41 毫秒收到首字节，3.87 秒下完；20000 行、id 无重复、每行 4 列。</result>
    <output file="output/stream-20000.txt"/>
  </claim>

  <claim id="ruling-streaming" judge="human" from="本地开发服务器 localhost:8787，feat/export @ a41c9e2" capturedAt="2026-11-28T06:12:40Z">
    <title>大批量导出改成流式，不在服务端生成完整文件</title>
    <ask>设计写的是“先生成完整文件，再一次性下载”，实现没有这样做。如果用户需要断点续传，或者需要下载中断后拿到的一定是完整文件，这个决定就是错的。</ask>

  </claim>

  <claim id="ruling-quoting" judge="human" from="本地开发服务器 localhost:8787，feat/export @ a41c9e2" capturedAt="2026-11-28T06:12:40Z">
    <title>含逗号、引号或换行的字段按 RFC 4180 加引号</title>
    <ask>设计没有写字段里出现逗号时怎么处理，这是我补的。如果只用 Excel 的人不该在文件里看到引号，或者下游是按逗号直接切分而不解析引号，这个决定就是错的。</ask>
    <p>title 和 body 里会有逗号和换行，不加引号列就会错位。RFC 4180 是最通用的写法，代价是原始文件里会出现引号。</p>
  </claim>

  <gap id="worker-deployed">
    <p>没有在真实部署的 Worker 上验证 20000 条导出的内存表现。原因：改成流式的理由正是 Worker 的内存上限，而本地开发服务器不受这个上限约束；部署是对外操作，需要你先同意。需要你做的一件事：允许我把这个分支部署到预览环境，或者豁免这一条。</p>
  </gap>
</verify>

**6. write** — `.artideck/artifacts/document/export-design/doc.xml`(スペックへの書き戻し、全文)

```xml
<doc>
  <h1>CSV 导出</h1>
  <h2>导出格式</h2>
  <p>每条笔记一行：id、title、body、updatedAt。UTF-8，逗号分隔。</p>
  <h2>大批量导出</h2>
  <p>超过 10000 条时，先在服务端生成完整文件，再一次性下载。</p>
  <p><ref verify="export"/> 实现与此不同：服务端不生成完整文件，改为流式输出，每 500 条写一次。</p>
  <h2>权限</h2>
  <p>只能导出自己的笔记。</p>
  <h2>实现结论</h2>
  <p><ref verify="export"/></p>
  <p>与设计不同的决定：</p>
  <ul>
    <li>大批量导出改成流式，每 500 条写一次，不在服务端生成完整文件。原因：一万条以上的完整文件在 Worker 上超出内存。如果用户需要断点续传下载，这个决定就是错的。</li>
    <li>（设计未规定）字段按 RFC 4180 加引号。原因：设计没有写字段里的逗号怎么处理。如果只用 Excel 的人不该看到引号，这个决定就是错的。</li>
  </ul>
  <p>踩过的坑：</p>
  <ul>
    <li>流式导出的测试一直挂起。根因：数据库游标在最后一批之后没有关闭，连接池被耗尽。绕法：在 finally 里关闭游标，并给测试加了 2 秒超时。</li>
  </ul>
</doc>
```
