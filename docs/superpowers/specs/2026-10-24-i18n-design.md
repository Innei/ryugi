# Ryugi i18n: English by default, Chinese when the browser asks

## Intent

Every user-facing surface of Ryugi is written in Chinese today. People arriving from the README, a shared cloud link, or the landing page who don't read Chinese can't use it. English becomes the default; Chinese stays available for browsers that prefer it.

## Decisions

- **Default English.** Any browser whose preferred language is not Chinese gets English.
- **Chinese is optional.** A browser whose preferred language is `zh` or `zh-*` (zh-CN, zh-TW, zh-HK…) gets Chinese. Only these two languages ship.
- **No language switcher in v1.** The language follows the browser. Nothing is persisted (no localStorage, no cookie, no URL parameter).
- **Scope is everything user-facing, in both repos**: `ryugi-artifacts` (this repo) and `ryugi-cloud`.
- **Web apps use react-i18next**: the artifacts viewer and the cloud admin (`ryugi-cloud/admin`).
- **Everything rendered outside a React app uses hand-maintained JSON dictionaries**: the local server's HTML pages, cloud server-rendered pages, cloud API messages, emails, and the landing page build.
- **The landing page stays static.** The build prerenders it twice, English (`home.html`) and Chinese (`home.zh.html`). The Worker picks one by `Accept-Language` and serves it at the same URL (`/home` joins `run_worker_first`; the response carries `Vary: Accept-Language`). The page records its locale so `client.tsx` hydrates with the same one.
- **Waitlist approval email** is sent in the language the user's browser asked for when they joined the waitlist. That language is stored on the waitlist row. Rows without it get English.
- **Social link previews** (`ryugi-cloud/src/viewer/social-meta.ts`) are always English: crawlers rarely send a language header.
- **Telegram ops alerts** (`ryugi-cloud/src/monitor/telegram.ts`) stay as they are; only the owner reads them.
- **Server error messages are translated in the viewer by error code.** Cloud error responses keep their English `error` message and every one carries a stable `code` (plan-limit errors already do; the other ~47 `HttpError`s gain one). The local server passes `code` through unchanged. The viewer looks the code up in its own dictionaries and falls back to the English message for an unknown code. CLI output stays English because the CLI never translates. The cloud does not read `Accept-Language` for JSON responses.
- **GitHub sign-in failures** (`auth.controller.ts`, `github.service.ts`) become an HTML error page, like `waitlistPage`, rendered from the JSON dictionaries by `Accept-Language`, instead of raw JSON in the browser.
- **The pass verdict stores English.** `useVerdicts.ts` posts `Pass` as the comment body instead of `'通过'`: comment bodies are data the agent and other reviewers read, so they don't follow the clicker's language. Existing `'通过'` comments are left as they are. *(Claude's call.)*

## Non-goals

- A language picker, saved preference, or per-user language setting (beyond the waitlist row above).
- Translating artifact content. Boards, documents and HTML pages the agent writes are shown as written.
- Agent-facing text. CLI output, skill files, `warnings.json` and JSON responses are already English and stay English.
- Languages other than English and Chinese.

## Anti-goals

- A Chinese user seeing English flash before the page switches.
- A cached Chinese page served to an English browser, or the reverse.
- A Chinese string missing from the Chinese dictionary going unnoticed, or an English key missing and showing a raw key to a user.

## Locale resolution

One rule everywhere: walk the preference list (`navigator.languages`, or `Accept-Language` by q-value); the first entry whose primary subtag is `zh` selects Chinese, the first entry whose primary subtag is `en` selects English, and if neither appears, English. `<html lang>` is set to `en` or `zh-CN` to match.

## Dictionaries

- English is the source of truth. The current Chinese copy becomes `zh`; the English copy is newly written, in the plain, short voice of the current Chinese.
- Both mechanisms use the same JSON shape: nested keys, `{{name}}` interpolation (i18next's default), and i18next plural suffixes (`_one`, `_other`) where counts appear.
- Times, dates, numbers and relative times ("1 minute ago") are formatted with `Intl` for the resolved locale, not hand-written strings.
- Lobe UI / antd built-in component text follows the same locale through their provider.
- A test per dictionary set asserts `zh` and `en` have identical key sets.

## Tests

`ryugi-artifacts` has ~50 test files that find elements by Chinese text. They move to English text (the default locale in the test environment), plus focused tests that render in `zh` to prove the Chinese path works. The same applies to `ryugi-cloud` tests that match Chinese.

## Release

`artifacts/src/` changes ship as a `ryugi-artifacts` release (version bump, tag). The cloud pins the viewer version, so cloud links pick up the translated viewer when the pin moves.

Error codes are a cross-repo contract, so the order matters: deploy the cloud with `code` on every error first (an old viewer ignores the extra field), then release the viewer that reads it, then move the cloud's viewer pin.

## Left to the builder

- File layout of dictionaries and how many namespaces.
- Key naming.
- Whether the JSON lookup helper is shared between repos or duplicated (it is small either way).
- The English wording, within the voice above.
- The migration that adds the locale column to the waitlist table.
- Order of work across surfaces, within the release order above.
- Error code names.
- Whether dictionaries are bundled or loaded lazily; how landing hydration fits the CSP; how `/home` caching works with `Vary`; Excalidraw's UI language; whether a repeat waitlist application updates the stored language.
